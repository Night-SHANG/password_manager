# Existing plaintext CSV export boundary

This work retains the existing six-column CSV and explicit plaintext-risk acknowledgment. It exclusively creates the requested final file and never deletes, truncates, renames, or overwrites an output after a failure. No plaintext temporary or recovery copy is created.

A precreation failure reports `NotCreated`: this operation did not obtain a new output handle. An unrelated preexisting file may still exist. Every failure after creation reports `MayRemain`, including identity failure before the first byte. Empty, partial or complete plaintext may remain at the attempted location or elsewhere if an external actor moved it. Diagnostic observations do not authorize deletion. Newly created parent directories also remain.

Success requires explicit serialization completion, flush, file sync, identified bounded SHA-256 readback, then a final full-target identity/length observation while retaining the original handle. It means those observations succeeded; it is not a simultaneous atomic pathname/content snapshot, a filesystem compare-and-swap, a lasting ownership claim, or a parent-directory power-loss commit. Use a stable local directory without hostile concurrent writers. Linux same-user/privileged writers and ancestor replacement can invalidate a later path or content; Windows read-only sharing reduces interference while the original handle is open.

The intended implementation uses csv-core 0.1.13 with caller-owned zeroizing chunks, sha2 0.11's zeroize feature and zeroizing readback/digest owners. Active-entry secrets are decrypted one at a time through storage's direct iterator. This bounded application-owned memory claim excludes compiler/register/backend copies, toolkit memory, OS cache, swap, dumps, storage copies and abrupt termination. Removal is never described as secure erasure.

A retained-output warning is independent of Settings, the current session and ordinary status. Its full attempted path remains visible through navigation, locking and recovery until explicitly acknowledged. Another export is blocked until that acknowledgment. Normal window close locks first and requires a current warning-bound confirmation when a notice remains. Both final close paths enter a terminal admission state before returning the window-close action, so queued same-batch export/unlock messages cannot start new work. Invalidated picker completions, completed screenshot-protection results, native security/clipboard completions and the existing generation-bound clipboard acknowledgment can still drain while a close warning is shown. Acknowledgment confirms understanding of the risk, not verified removal.

The GUI exporter runs on the single owned vault worker. Native lock and raw close observations revoke authority before deferred UI messages; the UI masks immediately and remains in a finishing state until actual cleanup. A write that already acquired its exact commit lease completes serialization, verification and cleanup despite later cancellation. A blocked OS write/sync/read can therefore keep the application masked and finishing indefinitely. Normal final close waits for both cleanup and consumption of the retained terminal outcome, then requires any current-generation plaintext warning confirmation. The synchronous public export API remains available to library callers. Forced process termination, panic-abort, power loss and OS-forced shutdown can bypass the warning; the in-memory notice does not survive restart, and startup does not scan/delete CSVs.

Linux files are created with mode 0600 (umask may restrict further). Windows retains inherited parent ACLs, not a new owner-only DACL; unsupported device/alternate-stream targets are rejected before file creation. Tests use synthetic local files; remote filesystem error/durability semantics and actual Windows 10 acceptance require separate platform evidence.

## Supported destinations and deliberate safety rejections

The existing ordinary-file identity and local-filesystem adapters are reused without changing the encrypted transaction algorithm. This narrows CSV admission compared with an arbitrary `OpenOptions` path:

- Linux accepts local filesystem types with magic values `0xef53` (ext-family), `0x58465342` (XFS), `0x9123683e` (Btrfs), `0x01021994` (tmpfs) and `0x794c7630` (overlayfs used in CI). Other types, including NFS/CIFS, are refused before creating the CSV. This is a conservative supported-type list, not a claim all mount/remote-storage arrangements have been detected.
- Windows accepts ordinary disk/verbatim-disk paths on volumes reported as fixed disks or RAM disks. UNC and verbatim UNC paths, device namespaces, alternate-data-stream components and reserved DOS device names are rejected before plaintext creation. Mapped network volumes are rejected by the drive-type check. A substituted or remotely backed volume is not given a stronger guarantee than the OS observation.
- Other operating systems have no supported adapter and fail before output creation. Parent creation can leave empty directories even when a later filesystem check rejects export.
- The final parent must be a physical directory acceptable to the adapter. Final symlinks/reparse points, directories and existing files cannot be replaced. Readback rejects nonregular outputs and hardlink aliases. Ancestor links or replacement are not comprehensively prevented; the original full attempted path is re-opened for verification, without lexical removal of `..`.
- Ordinary relative, nested and Unicode paths continue to work within those boundaries; no `.csv` extension is required. Invalid/empty paths and create collisions are `NotCreated`, which never means an unrelated file is absent.

These are safety refusals to avoid claiming local exclusive-create and verified-output semantics on unverified storage backends. Choose a stable supported local directory, then manually transfer a successful export if necessary; the application does not do that transfer automatically.

## Buffer ownership and dependency review

`csv-core = 0.1.13` is an added direct dependency already present through `csv = 1.4.0`. The latter remains for import and differential tests. The pinned csv-core writer contains configuration, quote-state flags and a byte count, with no private plaintext byte buffer or I/O destructor. Production passes six borrowed fields, including the entire initial field for necessary-quote decisions. Caller-owned 8192-byte chunks are wiped after explicit drains and on drop. Regression chunks of 2, 3 and 7 bytes test closing quotes, doubled quotes, UTF-8 splits and terminators; sizes below 2 are refused.

`sha2 = 0.11.0` enables its existing `zeroize` feature. It forwards to `digest = 0.11.3` and `block-buffer = 0.12.1`; their enabled Drop implementations wipe buffered bytes and core state. A compile-time trait assertion covers `Sha256: ZeroizeOnDrop`. Expected/observed digests finalize directly into owned zeroized 32-byte arrays; verification uses an owned zeroized 8192-byte read buffer. Test-only live-storage probes run after explicit wiping and before deallocation, never by reading freed memory. Late write/read faults first place a unique synthetic secret in the named buffer; further unwind cases occur after readback hashing and while both digest arrays are live. Private dependency temporaries (including digest core finalization copies) are not inspected or covered by those probes. The dependency lock delta adds only the direct csv-core edge and the existing digest/block-buffer zeroize edges; no version upgrades are involved.

## Regression evidence and remaining acceptance

The regression suite includes baseline failures for unsafe failure deletion, replacement reported as success, Linux permissions, the missing normal-close route and warning loss after lock. Export tests inject create/identity/write/reveal/flush/sync/open/read/metadata/checkpoint failures, first/partial/zero/interrupted writes, diagnostic failure, moved/replaced/aliased targets, same-inode corruption, bounded extra/short reads and caught unwind. The non-destructive I/O interface has no deletion/rename/truncation capability, with a source guard against bypassing it. Synthetic child-process termination demonstrates that plaintext can remain without destructor cleanup or restart scanning.

App and headless GUI tests exercise the actual export handler, admission gates, navigation/lock/recovery notice retention, repeat-export blocking, generation-bound acknowledgment and normal-exit controls, and long Unicode paths at 960×640, 1280×800 and 1600×900. An entered-export barrier test now proves the actual GUI handles lock while the worker is held after output creation. A separate delayed-observer regression proves final close cannot overtake a late retained-output warning even after the worker has drained. Headless geometry/captures do not establish actual Windows 10 OS event, ACL, sharing, DPI, IME, storage durability or power-loss behavior. Windows-native sharing/device-path tests run only on Windows and must pass on the exact published source revision before that evidence is claimed.

### Platform-aware regression fixtures

A clipboard-cleanup failure raised while close revokes the native permit can advance the warning generation. Tests acknowledge the token rendered after close and separately deliver a later native failure to prove that an older token cannot dismiss the new warning. Production generation checks are unchanged.

Windows directory rename has an additional open-descendant restriction; permitting delete sharing on a child file does not make an ancestor rename a valid cross-platform fault schedule. The native Windows test expects that competing parent rename to be denied while the child is open, verifies successful unchanged export, then retries the rename only after all export handles have closed. Linux tests exercise real parent replacement at both verification checkpoints. A separate, explicitly modeled pathname-resolution test runs on both platforms and rejects an equal-content competitor with a different identity. See [Microsoft's directory rename rules](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information#remarks) and [the Windows file-store rename algorithm](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/87f86c9b-6c2a-4803-84b7-131a74a434fa).

Namespace mutation errors fail the test fixture directly; they must never masquerade as an expected exporter I/O failure. Completed-schedule markers and labeled identity/observation assertions distinguish successful fault injection from OS-denied interference. Linux model results do not establish the Windows-native outcome; that test must run in Windows CI.
